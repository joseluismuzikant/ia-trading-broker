Help and glossary

What this application does today, how a run turns broker data and a model answer into a proposal, and plain-language definitions of the business and technical words on the other pages.

Nothing is traded without you. Analysis, the allocation, and the before/after portfolio are simulated previews. Real orders are sent to the broker — InvertirOnline (IOL) for the MVP — only after you approve the plan and press the execution buttons yourself, one confirmation for the sales and one for the purchases. Until the IOL trading terms are configured, every execution is blocked and says why.

What this is

ia-trading-broker is a portfolio assistant for accounts reached through a broker API. On demand it reads the account, builds a simulated portfolio from it, calculates technical indicators, and asks a portfolio analyst — a language model — how the whole account should be allocated. The answer is checked in Python, saved as a proposal, and reviewed by a person before anything happens.

Two kinds of reasoning end up on a proposal. The analyst answers for the portfolio as one whole: a target allocation, one target weight per symbol plus cash, with the reasons and the risks in its own words. The fixed rule-based policy still produces the order list shown next to it. Both are evidence for your review, and a review tool is exactly what this is: it does not trade on its own and it does not promise returns.

What it can and cannot do

Today the application can:

  • Connect to a broker account through an encrypted, saved login — IOL for the MVP — and read the profile, balances, and country portfolio.
  • Save every broker response as a timestamped snapshot, and keep the last good one, labelled stale, when the broker is down.
  • Build a paper ledger, a simulated account, from the current portfolio.
  • Refresh daily price history and compute technical indicators from it.
  • Ask a selected model for a whole-portfolio target allocation, validate that answer against the account and the configured limits, and show it on the review page with the model's reasons, risks, and provenance.
  • Turn the validated target allocation into exact trades in deterministic Python: whole units, sales before purchases, self-financing.
  • Save an immutable proposal and wait for your decision. Approving it executes the sales — and, after a second confirmation, the purchases — against the real broker.
  • Reconcile every submitted order with the broker: filled, partially filled, pending, cancelled, or rejected, with the actual executed quantity and price.
  • Record every step in a local history, and print a proposal to PDF.

It does not:

  • Trade on its own. A person approves every plan and separately confirms each execution phase; nothing is sent automatically.
  • Claim an execution the broker has not confirmed. An accepted order is pending until IOL reports it as filled.
  • Assume new money or unsettled proceeds. Buys are funded only by cash the broker actually reports as available.
  • Trade intraday. It reasons on daily data, and it is built for an existing portfolio rather than for market timing.
  • Guarantee results. A model answer is advice to review, not investment advice.

How a run works

  1. Read the broker. A saved connection logs in to the broker and fetches the profile, account status, and country portfolio. Each response is stored as a timestamped snapshot.
  2. Build the paper ledger. The portfolio snapshot is copied into a simulated account holding fake cash and fake positions. Creating it costs no broker calls.
  3. Refresh price history. For every symbol the analysis will judge, recent daily prices are read and saved. These are read-only calls.
  4. Calculate indicators. EMA, RSI, MACD, ATR, average volume, and the return are computed in Python from that history.
  5. Ask the portfolio analyst. The whole account — holdings, current weights, evidence, watchlist, and limits — goes to the model chosen on the form, in one request. It answers with a target allocation: a weight per symbol, a cash weight, and its reasons and risks.
  6. Validate the answer. Python checks it against the account: every holding covered, no invented symbols, weights between 0% and 100% adding up to 100%, the cash floor respected, and actions consistent with the moves. An answer that fails is refused, and the run stops without a proposal.
  7. Size the trades. The validated target allocation is turned into exact trades in deterministic Python: whole units rounded down, sales before purchases so the proceeds fund them, never selling more than is held or spending money the account does not have.
  8. Save the proposal. The full plan is stored once: the validated target allocation with the model's provenance, the exact trades, the simulated portfolio before and after, and the warnings. It is shown on the Analysis and Proposals pages. Nothing is sent to the broker.
  9. Wait for approval. The run pauses. The plan goes nowhere until you approve or reject it. An approval covers the whole plan and expires after 24 hours.
  10. Execute in two phases. Approving submits the sales to the broker; a second confirmation submits the purchases the broker's actual available cash covers. Every order is saved before it is sent and can be reconciled against IOL at any time.

There is no automatic mode. Every plan and every execution phase waits for a human decision.

The portfolio analyst

The analyst is a language model asked about the account as one portfolio, never symbol by symbol. It sees the cash, the positions and their current weights, the indicator evidence, the instruments it may mention, the portfolio limits, and any data warnings. It never sees credentials, it cannot place orders, and it never decides a quantity: it answers in weights and words, and deterministic Python does the rest.

What one answer contains:

  • Target allocation — a target weight per symbol and a target cash weight that add up to 100%. Zero target weight means exit; there is no shorting and no leverage.
  • Action — buy, hold, or sell, which must agree with the move from the current weight to the target.
  • Confidence, rationale, and risks — in words, per symbol, plus a short summary for the account as a whole.
  • Provenance — the provider, the model id, and the prompt version. It is stamped from the configuration, never believed from the model's own answer, so a saved proposal always says what produced it.

Which models may be asked is declared in config/models.toml: the label the interface shows, the model id, the provider, the endpoint, and the name of the environment variable that holds that provider's key. You pick one per run in the Analysis form. A run that needs a missing key fails with a clear message and saves no proposal — there is no silent fallback to another model or to a hardcoded answer.

One entry is not a model at all: the Fake simulator (smoke test). It is an offline simulator that answers with the portfolio kept as it is, needs no key, and reaches no network. Choose it to smoke-test the whole flow — ledger, analysis, validation, review, approval, and history — without spending a single API call. Its proposals say plainly that a simulation produced them.

Snapshots and freshness

Every broker response is saved as a snapshot: one row per connection and per kind of data (profile, account status, portfolio for a country, price history for a symbol). Pages always render the newest saved snapshot, so they load instantly and never wait on the network.

When you press Refresh from IOL and the broker fails, the last good snapshot is kept and marked stale. Known data is never deleted. That is why you can still read the last portfolio even when IOL is down.

How the code is organised

The application is split into layers so a change stays in one place:

  • Pages (app/api) handle the web requests and render templates.
  • Services (app/services) orchestrate: they fetch, save snapshots, build the ledger, and run an analysis.
  • IOL adapter (app/infrastructure/iol) is the only place that knows IOL field names, endpoints, tokens, and the call budget.
  • Model adapters (app/infrastructure/openai, app/infrastructure/simulation) turn one model catalog entry into an analyst that answers. The simulator is the offline one; both sit behind the same contract (app/ports), so swapping providers is configuration, not surgery.
  • Domain (app/domain) holds the broker-agnostic models and the pure logic: money, portfolio, indicators, strategy, sizing, and risk. IOL never leaks here.

The paper ledger

A paper ledger is a simulated portfolio: a pretend account of fake cash and fake positions, used to practise trading without real money. You create it with one button, and it is copied from the newest portfolio snapshot for that country.

It records:

  • Cash — pretend free money, taken from the last saved account status.
  • Positions — one row per symbol, with a quantity, an average price, a last price, and a market.
  • Totals — positions value, and total value (cash plus positions).

The ledger is the book the strategy and the risk checks reason about. A decision changes the ledger, never the real account. Creating it contacts IOL zero times, so it costs no API calls.

Indicators

An indicator is a number computed from a series of prices, used to summarise price behaviour. All values here are calculated in Python from the saved daily history, and a value stays empty until its window has enough days.

EMA — Exponential Moving Average

A smoothed average that gives recent prices more weight than older ones, so it reacts faster than a plain average. The application uses a fast EMA(12) and a slow EMA(26). When the fast line is above the slow line, the recent trend is up.

EMA today = price today × k + EMA yesterday × (1 − k) where k = 2 / (period + 1). The first value is the simple average of the first period prices.

RSI — Relative Strength Index

A momentum gauge between 0 and 100. It compares the size of recent gains with recent losses. High values suggest the price has risen a lot already (overbought); low values suggest it has fallen a lot (oversold). The application uses RSI(14).

RSI = 100 − 100 / (1 + RS) where RS = average gain / average loss, both smoothed over the period.

How it is used: the strategy buys only while RSI is between 45 and 70, so it avoids buying something already stretched above 70, and sells when RSI is below 50.

MACD — Moving Average Convergence Divergence

The gap between a fast and a slow EMA, plus a smoothed version of that gap. It shows whether momentum is building or fading. The application uses the standard 12 / 26 / 9.

  • MACD = EMA(12) − EMA(26)
  • signal = EMA(9) of the MACD
  • histogram = MACD − signal

How it is used: a positive histogram means momentum is turning up. The strategy requires it for a buy.

ATR — Average True Range

A measure of how much the price moves in a day, including gaps. It is a volatility number, not a direction. The application uses ATR(14). It is shown as context for how large normal daily swings are.

Supporting numbers

  • Average volume (20 days) — how much is normally traded, a liquidity hint.
  • Return — the fraction the price changed over a period.
  • Exposure — how much of the portfolio one position represents.

The strategy

The strategy is fixed Python, fully determined by its inputs. Given the indicators, it returns one action per symbol:

  • Buy when the fast EMA is above the slow EMA, RSI is between 45 and 70, and the MACD histogram is positive — an uptrend that is not already overbought.
  • Sell when the fast EMA is below the slow EMA and RSI is below 50 — a downtrend with weak momentum.
  • Hold in every other case, including when there is not enough history.

A missing indicator never produces a trade. The reason for every action is shown next to it on the Analysis page.

The strategy is one of two decision sources on a proposal; the portfolio analyst's target allocation is the other. Today the order list is still sized from the strategy's signals. Deriving order quantities from the model's target weights is planned work.

Sizing and risk checks

Sizing picks the quantity; the risk checks decide whether the order is allowed. Together they are the DecisionPolicy. Every check must pass for a recommendation to count as an order. A failed check sets the quantity to zero and is kept visible, so you can see exactly what was blocked and why.

Check Limit Applies to Meaning
finalists the finalists of the run buys Only an instrument the funnel picked may be bought. A held instrument outside it may still be reduced or sold, so the money is never trapped.
trade_limit 3 orders per run the whole run One run may place only a few orders, which is what bounds how much it can turn over at once.
position_size 15% of the portfolio buys One position may not grow past a fifteenth of the portfolio.
cash_reserve keep 10% in cash buys A buy may not spend the cash the account must keep.
category_cap 4 shares, 3 CEDEARs, 2 bonds buys Each kind of instrument has its own cap, so the portfolio cannot fill up with one of them.
open_positions 8 positions buys The account may hold only so many positions at once.
price a saved price every order An instrument without a usable price is held, never traded.
quantity whole shares, at least 1 every order Fractional and empty orders are rejected.
shares never more than held sells You cannot sell what you do not own.

The proposal

A proposal is a saved trade plan: the analyst's validated target allocation, and every rule-based recommendation with its evidence, its quantity, and its risk results, plus the portfolio value, the cash, and the plan turnover. It is the unit you review on the Analysis page.

  • Model target allocation — what the analyst answered: its summary, the current and target weights side by side, the action per symbol, the reasons and risks, and the provenance line. It is advice for the review, not an order list.
  • Approval mode is HUMAN_IN_THE_LOOP: a human is meant to decide. The alternative, AUTOMATIC, is not built.
  • Execution mode is PAPER: decisions affect the simulated ledger, never the broker.
  • A saved proposal is never edited. Running an analysis again creates a new one, so a review always points at exactly the plan that was risk-checked.
  • Export PDF. The review page can print the plan. The button opens a clean document with the funnel, the plan, the orders, the approval, and the timeline, and the browser's print dialog saves it as a PDF. The site navigation and the buttons are left out of the document.

Approval and execution

When a plan holds at least one order, the run stops and waits. The plan is frozen: the trades you review are the trades that can be sent, never recalculated afterwards. Approval records your decision and sends nothing by itself — each trade is executed separately, on your command.

  • One trade at a time. Every trade has its own Execute button with a quantity prefilled with the plan's suggestion and editable. Run it whenever the portfolio allows it: a sell needs the units still held, a buy must be covered by the cash IOL actually reports.
  • Retry one by one. A trade the broker rejected or cancelled is a proven failure and offers Retry. An order the broker may still act on — or whose outcome is unknown — is never resent; it must be reconciled first.
  • Accepted is not executed. When IOL answers 201 the order is accepted — the broker took it. Only when IOL reports the units as operated is it a fill. The interface never claims more than the broker confirmed.
  • Reconcile at any time. Refresh Order Status re-reads each submitted order from IOL and records the actual executed quantity and price. A partial fill stays partial; the requested limit price is never shown as an execution price.
  • One decision, protected. Approving and rejecting are forms with a CSRF token, like every other action, and only the owner can decide. Rejecting sends nothing. A pending approval expires after 24 hours.
  • Nothing is sent twice. Every order is saved before it is sent and carries a key that identifies the trade, so a restart or a repeated click cannot duplicate a live order.
  • Live mode is explicit. Executing fails closed while the settlement term and order validity are not configured, instead of silently simulating a fill. Changing them requires editing the configuration and restarting; the page shows a LIVE TRADING badge on every plan whose orders go to the real broker.

The trading history

Every step is written to a local event log that pages can read without calling IOL: the run started, the plan created, the approval requested and decided, each order prepared, submitted, accepted, filled, partially filled, rejected or left unknown, and the reconciliation results. The History page shows the orders and these events for one connection.

Orders and events are added and never edited. Each entry is scoped to the signed-in user, so one account can never read another account's history.

How values are shown

Amounts are shown the way a local reader expects them: thousands separated by a dot and decimals by a comma, with the currency code after the amount — 99.895,16 ARS rather than 99895.16 ARS. A missing amount is shown as a dash, never as zero. The code is taken from the data (Peso_Argentino becomes ARS), so it is never guessed.

Timestamps are shown in local time with their offset from UTC, for example 2026-10-02 11:42:06 UTC-3, instead of the UTC the database stores. Every page and the PDF export show the same format, so a saved plan can be read next to a printed one.

When the number of a plan is shown — in the history, in an event, or in a link — it is labelled Proposal ID. The word Proposal on its own means the plan, not the number.

The IOL call budget

IOL is free up to a monthly number of API calls, set by IOL_MONTHLY_CALL_LIMIT (25,000 by default). Past that limit, each call costs money. To make sure the limit can never be crossed by accident, the application counts every call and refuses to send one once the budget is used up. Pages also show the running count (“IOL API calls this month”).

The counter lives in memory and resets each month, so it is a safety net, not an exact invoice. It is measured per running process.

Glossary

Paper trading
Trading against a simulated account instead of a real one. Real prices, fake money.
Paper ledger
The simulated portfolio this application trades against: fake cash, fake positions, real symbols and prices. It never touches your real account.
Instrument / symbol
A tradable thing, such as GGAL (a share). “Symbol” is its short code.
Position
A holding in one instrument: how many units you own and what they cost on average.
Broker connection
A saved login to one brokerage account — IOL for the MVP. The password is stored encrypted and never shown again, and everything read through it is scoped to the signed-in user.
Portfolio analyst
The language model asked about the account as one portfolio. It answers in weights and words, never in quantities or orders; Python validates the answer and owns every execution.
Model catalog
The list of models a run may ask, declared in config/models.toml: label, model id, provider, endpoint, and which environment variable holds the key. Nothing in the code names a model.
Target allocation
How the account should be divided once the plan is done: one target weight per symbol plus a target cash weight, adding up to 100%. It is the analyst's central answer.
Target weight
The share of investable capital one symbol should represent. A zero target weight means exit the position.
Investable capital
The money being allocated: current cash plus the market value of the positions held. It assumes no new deposits.
Advice
The analyst's whole answer: summary, per-symbol action, target weight, confidence, rationale, and risks. It is input to a review, never an instruction to trade.
Provenance
Which provider, model, and prompt version produced an answer. It is stamped from the configuration when the run starts, never believed from the answer itself.
Rebalance
The set of trades that moves a portfolio from its current weights to the target allocation. Sells release cash that funds the buys in the same plan.
Self-financing allocation
A target allocation that adds up to 100% including cash, so it can be reached with the money already in the account and no new capital.
Fake simulator
An offline entry in the model catalog that answers with the portfolio kept as it is: no key, no network, no API cost. Used to smoke-test the whole flow; its proposals are labelled as a simulation.
Smoke test
A short manual pass through the main flow — ledger, analysis, review, approval, history — to confirm the application works end to end.
Snapshot
A saved copy of one broker response, with the time it was fetched. Pages read snapshots, not the network.
Stale
A saved snapshot shown after a refresh failed. The data is old but not lost, so it is labelled instead of hidden.
Indicator
A number computed from a price series that summarises one aspect of price behaviour, such as trend or momentum.
EMA
Exponential Moving Average. A trend line that weights recent prices more. Fast above slow suggests an uptrend.
RSI
Relative Strength Index. A 0–100 momentum gauge. High means possibly overbought, low means possibly oversold.
MACD
Moving Average Convergence Divergence. The gap between a fast and a slow EMA, plus its signal line and histogram, used to read momentum.
ATR
Average True Range. A volatility measure: how much the price typically moves per day, regardless of direction.
Strategy
The fixed rule that turns indicators into a buy, sell, or hold for the rule-based order list. Plain Python, fully testable, and separate from the portfolio analyst's advice.
DecisionPolicy
Sizing plus the fixed risk checks. It decides how large an order may be and whether it is allowed at all.
Risk check
A single rule with a pass or fail result, such as the finalists check or the position cap. All checks must pass for an order.
Universe
The instruments the project may trade at all. Every ticker and its paper name live in one configuration file, config/universe.toml, grouped into Argentine stocks, CEDEARs, and bonds. Nothing in the code names a symbol.
Analysis funnel
How a run narrows the universe to a few trades: the market scanner keeps the strongest candidates on cheap price readings, the technical stage scores them, the fundamental/news stage picks the finalists, and the risk manager turns at most a few of those into orders.
Finalists
The handful of instruments that survived the funnel. Only they may be bought in that run; a held instrument outside them can still be sold.
Portfolio constraints
The hard limits the risk manager enforces: how many positions, how many per category, how large one position may be, and how much cash must stay in the account. They are declared in config/universe.toml next to the universe.
Turnover
The total value of all orders in one proposal, as a share of the portfolio. Shown for information; the run is bounded by the number of orders it may place.
Proposal
A saved, immutable trade plan: the validated target allocation from the analyst, plus recommendations, evidence, quantities, and risk results. The thing you review.
Proposal ID
The number of one saved proposal. It is what the history, the events, and the links point at, so it is labelled Proposal ID whenever the number itself is shown. The word Proposal on its own means the plan, not the number.
Approval mode
Who decides. HUMAN_IN_THE_LOOP means a person approves; AUTOMATIC is not built yet.
Execution mode
Where an approved plan goes. LIVE sends real orders to the broker; PAPER only updates the simulated ledger.
Approval
The recorded human decision on one plan. Approving submits the sales; the purchases need their own confirmation. A pending approval expires after 24 hours.
Per-trade execution
Running one trade at a time, with the amount you choose. Each trade has its own Execute button, prefilled with the plan's suggestion, and it can be run whenever the portfolio allows it.
Retry
Sending a trade again after a proven failure (the broker rejected or cancelled it). An order still at the broker, or whose outcome is unknown, is never retried until it is reconciled.
Order
A saved intent to buy or sell one instrument: symbol, side, quantity, and limit price. An order is written down before anything is submitted, so it can never be sent twice.
Operation number
The identifier IOL returns when it accepts an order (numeroOperacion). It is what reconciliation reads to find out what really happened.
Accepted
The broker took the order. It has not necessarily executed yet. Only a fill means money or shares changed hands.
Fill
The part of an order that actually executed, with the quantity and price the broker reports. A partial fill is never treated as a complete one, and the requested limit price is never shown as the execution price.
Partial fill
Some units of an order executed and the rest is still working. The order stays open for reconciliation and is never resent.
Reconciliation
Re-reading a submitted order from IOL to record its real state: filled, partially filled, pending, cancelled, or rejected. Refresh Order Status does this; it only reads.
Resume execution
Continue a paused or interrupted plan until every order is submitted: it refreshes the orders already at IOL, then sends whatever is still missing — sales first, then purchases. It never resends an order the broker already has, so it is safe to press repeatedly.
Idempotency key
A stable name for one order, built from the proposal and the symbol. A repeated submission finds the same order instead of creating a second one.
Event log
The local, append-only record of what a run did. It is what the History page shows.
Call budget
The monthly cap on IOL API calls. The application counts calls and refuses to send one when the budget is spent.
Tenant isolation
Every query is scoped to the signed-in user. One account can never read another account's data.
Snapshot time
The moment a snapshot was fetched. Shown on every broker-data page so you know how fresh it is.
CSRF token
A hidden value in every form that proves the request came from this site, blocking cross-site form submissions.

Reading the pages

  • Analysis — what the AI recommends: the portfolio summary, the current versus target allocation, the simulated portfolio after the recommendation, the AI summary, and the main risks. Technical details are collapsed at the bottom, and the saved proposal is linked at the end.
  • Proposals — every saved plan for your account, newest first, with its status, model, and number of trades. Each row offers View, Export PDF, and — when no order is waiting at the broker — Delete.
  • Proposal — what exactly you are about to execute: the allocation, the sales and purchases tables, the cash summary, the risks, and the decision. After approving, each trade gets its own Execute button with an editable quantity; a failed trade offers Retry, and Refresh Order Status reconciles with IOL.
  • Order status — per order: quantity, filled quantity, executed price, status, and the IOL operation number. Accepted means the broker took it; only filled means it executed.
  • History — the append-only event log of everything the application did.
